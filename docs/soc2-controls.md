# KeyQuorum SOC 2 control map

This maps the AICPA Trust Services Criteria (2017, revised points of focus
2022) to the technical controls this repository implements, and to the
evidence an auditor can check: a test, a workflow, or a file and line. It is
**not** a SOC 2 report. A report covers an operating organisation over a
period. Most of the common criteria (CC1 to CC5: governance, people, risk
assessment, monitoring of controls) and the physical controls belong to
whoever runs KeyQuorum. The [operator responsibilities](#operator-responsibilities)
section lists what the software relies on the operator to provide.

Keep this file in step with the code. A change to a control named here
updates its row in the same pull request (see "Other agent instruction files"
in `AGENTS.md`).

## Operator responsibilities

The software relies on whoever runs it for these. An auditor should look for
them in the operator's own controls.

- **TLS** (CC6.7): terminate TLS 1.2 or later in front of every relay that is
  not on loopback, with a publicly trusted certificate. The relay itself
  serves plain HTTP. On Cloudflare the edge
  terminates TLS, and the operator owns the minimum TLS version and the edge
  certificate configuration (`docs/operator/relay-hosting.md`).
- **Rate limiting and WAF** (CC6.6, A1.2): the native relay limits requests
  per client per minute. Behind a proxy it trusts only the last
  `X-Forwarded-For` entry, so the proxy must set that header. Add connection
  limits and a global request ceiling in front of the relay; its limiter does
  not cover those. On Cloudflare, rate limiting at the edge and the WAF rules
  are the operator's: `deploy/cloudflare/terraform/` holds a rate-limit and a
  cache-bypass ruleset for the customer routes, written, accepted by CI's `terraform validate` and never planned or applied
  against a real account, and the relay it fronts has never been deployed. The
  Worker also limits each client address itself (`RATE_LIMITER`, 300 per 60 s,
  keyed on `CF-Connecting-IP`).
- **Backups** (A1.2, A1.3): back up the relay database and personal stores with
  SQLite's online backup (`sqlite3 <db> ".backup <file>"`), keep the copies
  owner-only, and test a restore. `file reindex` rebuilds the tracked-file
  index from `.kqtf` containers, but the containers themselves need backing up.
  On Cloudflare, the relay's Durable Object
  has point-in-time recovery, which this repository has not verified; the
  operator confirms it, restores, and verifies the restored audit chains
  against the newest operator-held checkpoint before serving (see Log
  retention).
- **Cloudflare account and secret custody** (CC6.1, CC6.7, CC6.8; the
  pipeline and the Worker exist, nothing is deployed and the setup below is not done): the operator
  owns the Cloudflare account, zone and domain; creates the GitHub
  environments `cloudflare-staging` and `cloudflare-production` (production
  with a required reviewer) with the Workers-deploy token (Workers Scripts edit
  only), the account id and the variable `RELAY_URL`; runs `terraform apply`
  locally with a separate token, and keeps its state and `terraform.tfvars` off
  shared storage; sets the relay key and certificate as
  Worker secrets with `wrangler secret put`, never as GitHub secrets; and
  keeps the `kql_…` operator lock and the provider-root key off every Worker.
  For the admin Worker (the code exists, nothing is deployed or configured):
  create the Cloudflare Zero Trust organisation, set `operator_emails`, apply
  Terraform with `admin_environments` (an Access application per
  admin hostname; the Worker also verifies the Access token itself), then set
  the GitHub environment variables `ACCESS_TEAM_DOMAIN` (from the Zero Trust
  dashboard), `ACCESS_AUD` (the `admin_access_aud` output) and `ADMIN_URL`
  (for the smoke test). They are not secrets. Also turn on Access's
  independent MFA with a hardware security key and enrol it and a spare
  (`deploy/cloudflare/terraform/README.md`, "Operator login and MFA"); nothing
  in the repository enforces or checks it, and the Terraform's
  `idp_mfa_required` applies only to an IdP that reports MFA. The relay uses the
  owner's domain `keyquorum.dev`, mounted under `/relay`, and the console has its
  own path (`/relay/admin`, staging `/relay/staging-admin`) of the same origin;
  applying the Terraform rulesets would replace any existing rules in that
  zone's two entry-point phases unless they are imported first, and the zone
  must be on the owner's Cloudflare account. Cloudflare Notifications
  and the R2 retention lock are set in the dashboard
  (`docs/operator/relay-hosting.md`).
- **Subprocessor** (CC9.1; nothing is deployed yet): Cloudflare terminates
  TLS and can see bearers in transit, and the Cloudflare account and its API
  tokens are the root of hosting trust. The operator records it as a
  subprocessor and reviews its own assurance reports. Cloudflare Access also
  holds the operator identities and signs the token the admin Worker checks;
  the Worker fetches Access's public key set from Cloudflare (5 s timeout,
  cached an hour, refused on failure).
- **Log retention** (CC7.2): keep the relay's stderr log (WARN denials, TTL
  purges) and the `api_key_events`, `provider_auth_events` and
  `audit_anchors` tables for the period the audit requires. Run the
  verification regularly and keep its output. Take a checkpoint
  (`host keys checkpoint --out FILE`) on a schedule, at least daily and
  after every key ceremony, and keep each one off the host in write-once
  storage you control; verify with the newest (`keys events --verify
  --checkpoint FILE`). A chain is tamper-evident, but someone who can write
  the database could delete the newest rows along with their anchors, and
  an anchor's own date is only its signer's word: the checkpoint is what
  bounds both, to the time since it was taken.
- **Key ceremonies** (CC6.1): generate the provider root key offline, keep its
  owner-only file off networked hosts, and record who held it.
- **Branch protection** (CC8.1): require the `test`, `lint`,
  `rust dependencies`, `secret scan`, `lab dependencies`, `codeql gate` and
  `workers` checks, and a human review, before merging to `main`. The checks
  `mongodb store`, `helm chart` and `container image` no longer exist; remove
  them from the branch protection rule (a GitHub setting, not changeable from
  this repository), or merges wait on a check that never reports. The
  operator must also add `workers` to the rule; this repository cannot, and
  until it is added a failing Workers check does not block a merge. The
  `workers dependencies` job of `security.yml` is not in this list; add it if
  the audit is to gate merges.
- **Host access** (CC6.1, CC6.2): limit shell access to the relay host. Anyone
  with it can read the relay database and, given the relay key, mint API keys.

## Known limitations

These are stated so an auditor need not discover them:

- The audit chain proves what was anchored. Rows written after the newest
  anchor are reported as pending until the relay signs them (at the next scan
  at the latest). Removing the newest rows together with their anchors can
  only be detected against an anchor kept elsewhere.
- An anchor's `signed_at` is the relay's own clock. A relay key that leaks
  while its certificate is valid can sign anchors until the certificate is
  revoked (`.kqrl`), and revocation then distrusts every anchor that
  certificate signed.
- The relay's rate limit is per process and per client address. It is not a
  defence against a distributed flood, and where several instances run each
  counts on its own, so a global ceiling belongs at the edge.
- A sealed `.kqkey` bundle written before a commit that then fails is
  compensated (the host removes it), not crash-atomic.
- Cloudflare hosting is partly built. Exists: the public Worker and its
  Durable Object running the relay core as WebAssembly (tested over the real
  core and run under local workerd, never deployed), the `workers` workflow and
  its tests, the Terraform, and the admin Worker with the provider's console and
  its binding to the Durable Object (issue #99), none of it deployed: **the
  Cloudflare relay answers every customer route with 401 until an operator has
  created the lock and issued a key from the console**. Production-only checks
  remain (peak
  memory of a 16 MiB page, row size, the bundle limit, the point-in-time
  recovery window, the overload bound, and that a Version URL answers 404). The
  Terraform was never planned or applied against a real account by its authors;
  CI's `terraform validate` accepts it and the committed `.terraform.lock.hcl`
  pins the provider (5.27.0). Cloudflare Notifications and the R2 retention lock
  are dashboard steps, not Terraform. The owner's setup (GitHub environments,
  secrets, `RELAY_URL`, `workers` among the required checks, Cloudflare account,
  zone and domain) is not done, and no deployment has run.
- Console: one operator role; a lost operator lock has no console or tested
  recovery on the Cloudflare relay; a lost bundle download is recovered by
  replacing the key, not by retrieving it; licences enforce nothing beyond the
  revocation and expiry of keys; activity is a usage view, not evidence, and
  does not count requests refused before the core; staging, restore, overload,
  storage growth and cost have not been measured (A1.2, CC7.2).
- Cloudflare terminates TLS and can see bearers in transit (CC9.1). There is
  no customer-managed encryption key for Durable Object storage; Cloudflare
  encrypts it at rest (C1.1).
- Durable Object point-in-time recovery is not verified by this repository
  (A1.2). The operator-held audit checkpoints and a restore drill are what
  bound a restore.
- Copies of plaintext that leave the process (stdout, an output file the user
  chose) are outside what zeroization can reach.
- Lab demo passphrases and seeded data are public on purpose
  (`.gitleaks.toml`) and protect nothing.
